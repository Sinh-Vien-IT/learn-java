## 1. GC Fundamentals 🔴

### Object nào được GC?

```
GC Root → reachable objects KHÔNG bị GC
GC Root → unreachable objects BỊ GC

GC Roots:
1. Local variables trong running threads' stacks
2. Active threads
3. Static fields của loaded classes
4. JNI references

Reachability:
  Object A ← GC Root   → A SỐNG
  Object B ← A          → B SỐNG (reachable from root qua A)
  Object C (no path)     → C CHẾT → eligible for GC
```

### Mark and Sweep

```
Phase 1 — MARK:
  Traverse từ GC Roots, mark tất cả reachable objects

  GC Root → [A ✓] → [B ✓] → [C ✓]
                                │
            [D ✗]   [E ✗]     [F ✓]
            (unreachable)

Phase 2 — SWEEP:
  Remove unmarked objects, reclaim memory

Phase 3 — COMPACT (optional):
  Move surviving objects contiguous → eliminate fragmentation
  → Cần update references → expensive
```

### Stop-The-World (STW)

```
GC cần pause tất cả application threads:
  → "Stop The World" pause
  → Trong thời gian pause: không có application code chạy
  → Latency spike!

Goal: minimize STW pause duration
  → Concurrent GC (run alongside application)
  → Nhưng 100% concurrent impossible — vẫn cần short STW pauses
```

## 2. Generational GC 🔴

### Generational Hypothesis

> "Hầu hết objects die young"

**Thực tế:** ~98% objects sống rất ngắn (temporary variables, request-scoped objects). Chỉ ~2% sống lâu (caches, singletons, connection pools).

→ Chia Heap thành generations, GC frequency khác nhau.

### Heap Generations

```
┌────────────────────────────────────────────────────────┐
│                        HEAP                             │
│                                                         │
│  ┌──────────────────────────────┐  ┌────────────────┐  │
│  │      Young Generation        │  │ Old Generation │  │
│  │         (~1/3 heap)          │  │   (~2/3 heap)  │  │
│  │                              │  │                │  │
│  │  ┌────────────┐ ┌───┬────┐  │  │                │  │
│  │  │   Eden     │ │S0 │ S1 │  │  │   Tenured      │  │
│  │  │ (~80% YG)  │ │   │    │  │  │                │  │
│  │  └────────────┘ └───┴────┘  │  │                │  │
│  │                              │  │                │  │
│  └──────────────────────────────┘  └────────────────┘  │
└────────────────────────────────────────────────────────┘
```

### Minor GC (Young GC)

```
1. Eden full → trigger Minor GC
2. Mark live objects trong Eden + S0 (hoặc S1)
3. Copy live objects → S1 (hoặc S0), increment age
4. Clear Eden + S0 (hoặc S1)
5. Objects age > threshold (default 15) → promote to Old Gen
6. Duration: typically ~10-50ms
7. Frequency: frequent (hàng giây nếu allocation rate cao)
```

### Major GC / Full GC

```
Old Gen full → trigger Major/Full GC
  → Mark-Sweep-Compact toàn bộ Heap
  → STW duration: 100ms → seconds
  → Frequency: ít hơn Minor GC nhưng impact lớn hơn

Full GC = GC toàn bộ Heap + Metaspace
  → Expensive, should be rare in well-tuned app
  → Frequent Full GC = memory issue (leak, wrong sizing)
```

### Premature Promotion

```
Problem: objects chưa dead nhưng bị promote lên Old Gen sớm
  → Old Gen fill nhanh → Full GC thường xuyên

Cause: Survivor space quá nhỏ → overflow → promote sớm
Fix: tăng Survivor space, tăng Young Gen size
```

## 3. GC Algorithms 🟠

### Overview

| GC | STW Pause | Throughput | Use Case |
|----|-----------|-----------:|----------|
| Serial | Long | High (single core) | Client apps, small heaps |
| Parallel | Medium | Highest | Batch processing, throughput-first |
| CMS (deprecated) | Short | Medium | Low latency (legacy) |
| **G1** | **Short-Medium** | **High** | **Default Java 9+, general purpose** |
| **ZGC** | **<1ms** | **High** | **Ultra-low latency** |
| Shenandoah | <10ms | High | Low latency (Red Hat) |

### Serial GC

```bash
-XX:+UseSerialGC
# Single thread, STW for all phases
# Use: small heap (<200MB), single CPU
# Not for production servers
```

### Parallel GC

```bash
-XX:+UseParallelGC
# Multiple threads for GC → higher throughput
# STW for all phases
# Use: batch processing, throughput > latency
# Was default before Java 9
```

## 4. G1 Garbage Collector 🔴

### Tại sao G1?

G1 = **Garbage First** — default GC từ Java 9. Balance throughput và latency.

### G1 Architecture

```
G1 chia Heap thành regions (1-32MB mỗi region):

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ E  │ E  │ S  │    │ O  │ O  │ H  │    │
├────┼────┼────┼────┼────┼────┼────┼────┤
│ O  │ E  │    │ O  │ O  │    │ O  │ E  │
├────┼────┼────┼────┼────┼────┼────┼────┤
│    │ O  │ O  │ E  │    │ O  │ O  │    │
└────┴────┴────┴────┴────┴────┴────┴────┘

E = Eden     S = Survivor     O = Old
H = Humongous (objects > 50% region)
(empty) = Free

→ Không fixed size Young/Old — regions dynamically assigned
→ GC chọn regions có nhiều garbage nhất → "Garbage First"
```

### G1 GC Phases

```
1. Young GC (STW):
   → Collect tất cả Eden + Survivor regions
   → Copy live objects → new Survivor/Old regions
   → ~5-50ms pause

2. Concurrent Marking (Mostly Concurrent):
   → Identify live objects in Old regions
   → Initial Mark (STW, piggyback on Young GC)
   → Concurrent Mark (concurrent with app)
   → Remark (short STW)
   → Cleanup (STW)

3. Mixed GC (STW):
   → Collect Young regions + some Old regions (most garbage)
   → Incrementally clean Old gen without Full GC

4. Full GC (STW — fallback, BAD):
   → Serial Mark-Sweep-Compact
   → Very slow, should NOT happen
   → Indicates: heap too small, allocation too fast, or leak
```

### G1 Key Parameters

```bash
# Target pause time (G1 tự adjust để meet goal)
-XX:MaxGCPauseMillis=200  # default 200ms

# Heap regions
-XX:G1HeapRegionSize=4m   # auto: 1MB-32MB based on heap size

# Initiating Heap Occupancy Percent (khi nào start concurrent marking)
-XX:InitiatingHeapOccupancyPercent=45  # default 45%

# Humongous object threshold
# Objects > 50% region size → allocate in humongous regions
# → Nhiều humongous = fragmentation → tăng region size
```

## 5. ZGC 🟠

### ZGC — Ultra-Low Latency

```
Z Garbage Collector:
  → Pause time < 1ms (sub-millisecond!) bất kể heap size
  → Heap support: 8MB → 16TB
  → Concurrent: gần như mọi phase concurrent
  → Production-ready từ Java 15+

Kỹ thuật:
  → Colored Pointers: metadata trong pointer bits
  → Load Barriers: check reference khi load (read barrier)
  → Concurrent relocation: di chuyển objects mà app vẫn chạy
```

### Khi nào dùng ZGC?

```
✅ Dùng ZGC khi:
  → Latency-sensitive (p99 < 10ms requirement)
  → Large heap (>4GB)
  → Không chấp nhận GC pause
  → Ví dụ: trading system, real-time API, gaming server

❌ Không dùng ZGC khi:
  → Small heap (<1GB) — G1 đủ tốt
  → Throughput-first (batch processing) — Parallel GC tốt hơn
  → Resource-constrained environment
```

### ZGC vs G1

| Feature | G1 | ZGC |
|---------|----|----|
| Pause time | 50-200ms | < 1ms |
| Heap size | Up to TBs | Up to 16TB |
| Throughput | Higher | Slightly lower (barriers overhead) |
| Concurrent | Mostly | Almost fully |
| CPU overhead | Lower | Higher (concurrent work) |
| Maturity | Very stable | Stable from Java 15+ |
| Default | ✅ Java 9+ | ❌ Must enable |

```bash
# Enable ZGC
-XX:+UseZGC

# Java 21: Generational ZGC (better performance)
-XX:+UseZGC -XX:+ZGenerational
```

## 6. GC Tuning 🔴

### Tuning Principles

```
1. Measure FIRST — đừng tune blind
2. Set goals: throughput? latency? footprint?
3. Start with defaults, tune incrementally
4. Monitor continuously
```

### Essential JVM Flags

```bash
# Heap sizing
-Xms4g                    # Initial heap (= Xmx để tránh resize)
-Xmx4g                    # Max heap

# GC selection
-XX:+UseG1GC              # G1 (default Java 9+)
-XX:+UseZGC               # ZGC

# G1 tuning
-XX:MaxGCPauseMillis=200  # Target pause time

# GC Logging (Java 11+)
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=100m

# Java 8 GC logging
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log
```

### GC Log Analysis

```
# G1 Young GC example:
[2024-01-15T10:30:15.123+0000][info][gc] GC(42) Pause Young (Normal) 
  (G1 Evacuation Pause) 
  2048M->512M(4096M)     ← 2GB → 512MB (heap 4GB)
  15.234ms                ← 15ms pause — OK for 200ms target

# Warning signs:
# → Pause > target (>200ms) = need tuning
# → Heap after GC close to max = memory pressure
# → Frequent Full GC = bad (leak or too small heap)
# → To-space exhaustion = survivor/old gen full
```

### Common Tuning Scenarios

**Scenario 1: Frequent Full GC**
```bash
# Possible causes:
# 1. Heap too small → tăng -Xmx
# 2. Memory leak → heap dump analysis
# 3. Too many humongous objects → tăng G1HeapRegionSize
# 4. Concurrent marking too slow → reduce IHOP

# Diagnosis:
-Xlog:gc*:file=gc.log  # check GC frequency và heap after GC
```

**Scenario 2: Long GC pauses**
```bash
# G1: giảm MaxGCPauseMillis (G1 sẽ collect fewer regions per cycle)
# → Trade-off: pause ngắn hơn nhưng GC frequency tăng

# Hoặc: switch sang ZGC cho ultra-low latency
-XX:+UseZGC
```

**Scenario 3: High allocation rate**
```bash
# Young Gen full quá nhanh → tăng Young Gen
-XX:G1NewSizePercent=30   # minimum young gen %
-XX:G1MaxNewSizePercent=60 # maximum young gen %

# Hoặc: giảm allocation rate trong code (object pooling, StringBuilder, etc.)
```

### GC Tuning Checklist

```
□ Set -Xms = -Xmx (tránh heap resize)
□ Enable GC logging
□ Monitor: GC frequency, pause time, heap usage
□ Target: Full GC should be rare (<1/hour)
□ Target: Young GC pause < 50ms
□ Heap usage after Full GC < 50% of max heap
□ Không tune quá sớm — fix code trước
```

## 7. Interview Questions

### Q1: "GC hoạt động thế nào?" 🔴

#### Strong answer
> "GC xác định objects unreachable từ GC roots (thread stacks, static fields, JNI), rồi reclaim memory. Java dùng generational GC vì hầu hết objects die young — chia Heap thành Young Gen (Eden + Survivors) và Old Gen.
>
> Minor GC collect Young Gen, frequent nhưng nhanh (~10-50ms). Objects survive qua nhiều GC cycles promote lên Old Gen. Major/Full GC collect Old Gen, ít frequent nhưng slow hơn.
>
> Default Java 9+: G1 GC — chia heap thành regions, GC chọn regions nhiều garbage nhất, target pause time configurable. Nếu cần ultra-low latency: ZGC (<1ms pause)."

#### Follow-up: "G1 vs ZGC?"
> "G1: default, balance throughput/latency, pause 50-200ms. ZGC: sub-millisecond pause bất kể heap size, slightly lower throughput. G1 cho general purpose, ZGC cho latency-sensitive systems."

---

### Q2: "GC tuning experience?" 🔴

#### Strong answer (Production example)
> "Có. Service xử lý Kafka events, p99 latency spike mỗi vài phút. GC log cho thấy G1 Mixed GC pause 500ms — vượt target 200ms. Root cause: quá nhiều humongous objects (Avro records > 50% region size = 2MB).
>
> Fix: tăng G1HeapRegionSize từ 4MB lên 16MB → objects không còn humongous → GC handle efficient hơn. Kết quả: pause giảm từ 500ms xuống 80ms.
>
> Lesson: luôn enable GC logging production, set alerts cho GC pause > threshold. Và đừng tune GC trước khi analyze log — measure first."

---

### Q3: "Stop-The-World là gì? Tại sao cần?" 🔴

#### Strong answer
> "STW là khi GC pause tất cả application threads. Cần vì GC cần consistent view — nếu app thay đổi references trong khi GC marking thì kết quả sai (miss live objects hoặc collect live objects).
>
> Modern GCs minimize STW: G1 làm hầu hết marking concurrent, chỉ STW cho initial mark và remark. ZGC gần như fully concurrent — STW < 1ms. Trade-off: concurrent GC tốn CPU hơn."
